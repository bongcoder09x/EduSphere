How the system is put together

Four client surfaces over one modular backend, with background workers and a fixed route shape.

Clients

Four surfaces, one record

Public site

Marketing, notices, results and the admission portal.

Admin & staff console

Records, admissions, finance and operations.

Faculty and gradebook

Attendance sessions, marks entry and mentees.

Student & parent portal

Attendance, marks, fees and transport.

Backend

Modular monolith

Each module owns its data and its service layer. Modules call each other in-process rather than over the network, so the system stays fast and any module can be separated later.

Auth / IAMTenancyAdmissionsStudentsFacultyAcademicsTimetableAttendanceExams & ResultsFees & PaymentsLibraryHostelTransportLearning materialCommsReportsFilesAudit

Workers

Background jobs, separate deployment

Long-running work stays off the request path; each worker scales on its own queue.

timetable-solver

builds clash-free class and exam timetables

pdf-renderer

ID cards, marksheets, receipts

notification-dispatcher

SMS, email, push, messaging

bulk-import

students and marks from spreadsheets

fee-reminders + late-fine

scheduled reminders and penalties

payment-reconciliation

settlement against ledger

report-builder

heavy exports to file storage
